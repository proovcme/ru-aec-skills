# Как предложить изменение в общий репозиторий

Если вы хотите улучшать установленные скиллы вместе со своим агентом, начните с [пользовательской инструкции и готовых запросов](IMPROVING.md). GitHub для этого не нужен. Эта страница — о передаче универсального изменения в общий проект.

Цель изменения — улучшить решение конкретной инженерной задачи, не увеличивая без необходимости объём инструкций и не превращая частный случай в универсальную норму.

## Сообщить об ошибке

Создайте Issue с названием скилла, ссылкой на строку и SHA коммита. Опишите задачу, минимальные обезличенные исходные данные, наблюдаемую ошибку и проверяемое ожидаемое поведение. Для нормативного замечания приложите обозначение и пункт документа, редакцию, изменения, проектную дату и официальное основание.

Не публикуйте персональные данные, переписку, материалы заказчика, модели, ключи доступа или внутренние отчёты. Для воспроизведения используйте самостоятельно составленный синтетический пример. Не копируйте чужие руководства и закрытые материалы.

## Исправить существующий скилл

1. Создайте fork и отдельную ветку. Прочитайте целиком затронутый `SKILL.md` и относящиеся к изменению references, проверьте входящие ссылки.
2. Воспроизведите проблему на минимальной задаче. Разделите дефект инструкции, недостаток исходных данных и ограничение доступных инструментов.
3. Сделайте узкую правку. Не добавляйте полный проектный цикл к локальной проверке; не требуйте не влияющих на результат данных. Аудит и объяснение не должны разрешать изменение модели или внешний выпуск.
4. Перепроверьте исходный случай и соседние сценарии, включая достаточные/недостаточные входы, границы метода и единицы. Для расчёта сравните результат с независимым способом или эталоном. Чтение инструкции и фактическое выполнение в BIM — разные виды проверки.
5. Проверьте Markdown, YAML, относительные ссылки и зависимости. Если меняется назначение или добавляется скилл, обновите реестр README.
6. Откройте Pull Request: что изменено, зачем, на каком основании, какие проверки реально выполнены и какие ограничения остались. Достаточно краткого обезличенного описания; не прикладывайте внутренние журналы или историю работы агента.

## Добавить новый скилл

Сначала проверьте, не решает ли задачу существующий скилл. Новый оправдан отдельной задачей и чёткой границей применения, а не просто новым номером СП.

Создайте папку с именем из строчных латинских букв, цифр и дефисов, короче 64 символов. В ней нужен `SKILL.md`:

```markdown
---
name: discipline-action-object
description: Какая задача решается и когда применять скилл.
---

# Название

Область работы, влияющие входы и границы вывода.
Метод выбора решения, проверки и требуемый результат.
Ссылки на подробности с условиями их чтения, если они необходимы.
```

Имя в YAML должно совпадать с папкой. Не заявляйте в description функции, для которых нет рабочего процесса. Сохраняйте краткий основной файл; существенные условные методики выносите в `references/`, повторяемую проверяемую механику — в `scripts/`, действительно используемые шаблоны — в `assets/`. Не создавайте пустые каталоги. `agents/openai.yaml` необязателен; при наличии его метаданные должны соответствовать скиллу.

Общие процессы подключайте относительными ссылками с условием чтения. Не копируйте их в каждый скилл, не создавайте циклы и не загружайте все references для любой задачи. Не добавляйте абсолютные пути, адреса локальных сервисов и зависимости от частной конфигурации.

## Нормативная база

Применяйте [общий нормативный маршрут](aec-govern-rf-capital-project/references/normative-workflow.md), включая раздел о поиске документов и проверке статуса.

- Разделяйте физическую зависимость, нормативный предел, договорное условие, ограничение конкретного оборудования и проектное допущение.
- Проверяйте полный текст нужного положения, область применения, определения, примечания, изменения, сроки действия и переходные условия. Указывайте полные реквизиты актов.
- Не закрепляйте «типовое» число без условий и источника. Не называйте весь документ обязательным по одной карточке «действует».
- Ссылочная база внутри скиллов — законы, НПА и нормативно-технические документы. Не добавляйте персональные методики, рекламные материалы и ссылки на авторские курсы. Напишите собственную краткую процедуру вместо копирования документов.
- Отсутствие доступа к источнику обозначайте как непроверенный статус. Не создавайте вымышленные цитаты, номера пунктов и заявления об актуальности.

## Проверка перед Pull Request

- Скилл выбирается для нужной задачи и не перехватывает несвязанные запросы.
- Локальная задача не требует полного комплекта проекта без технической причины.
- Влиятельное допущение явно ограничивает вывод; предварительная оценка не называется окончательным решением.
- Формулы воспроизводимы, единицы согласованы, коэффициенты и границы метода установлены.
- Значимые изменения проверены на реалистичном синтетическом случае без подсказки желаемого ответа проверяющему.
- Ссылки доступны внутри установленного комплекта; новый скилл добавлен в реестр и число скиллов обновлено.
- В публичных файлах нет частных данных и материалов без права распространения.

При наличии встроенного `skill-creator` можно использовать его валидатор `quick_validate.py` для каждого изменённого скилла. Это необязательная внешняя утилита: в данном репозитории её нет. Такая проверка структуры не подтверждает инженерную правильность или соответствие нормам.

## Права на вклад

Предлагайте только материалы, которыми вправе распоряжаться. Изменения оригинальных материалов принимаются на условиях [CC0-1.0](LICENSE). Не включайте сторонние тексты или код под несовместимыми условиями; ссылка на нормативный документ не меняет прав на его текст.
