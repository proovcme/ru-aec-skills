# Параметры, марки и ведомости

- Составь только необходимое соответствие: назначение → имя/идентификатор → тип данных и единица → тип или экземпляр → источник/формула → потребитель (марка, ведомость, расчёт). Тип изделия и установленная позиция не должны случайно управляться одним параметром типа.
- Общие параметры бери из согласованного определения. Совпадение имени не доказывает совпадение GUID; перед заменой сопоставь GUID, тип данных, значения, формулы, метки и привязки проекта. Не пересоздавай параметр с тем же именем в надежде сохранить совместимость.
- Не добавляй все параметры как общие: внутренним управляющим величинам это обычно не нужно. Параметры для пользовательских меток и межсемейного использования проверяй в реальной марке/спецификации. Не пытайся внедрить обычный параметр проекта внутрь RFA как параметр семейства.
- Для MEP различай отображаемое текстовое поле и физический параметр соединителя. Заполненная строка «расход» сама по себе не участвует в расчёте сети.
- Вложенный компонент делай общим (Shared), когда нужен отдельный учёт/выбор/маркировка и это соответствует модели изделия. Проверь, что ведомость не считает одновременно комплект и его детали как дублирующиеся позиции поставки.
- При локализации или адаптации не переименовывай и не удаляй массово параметры до проверки формул, каталогов типов, таблиц выбора, марок и внешних зависимостей. На копии проверь миграцию и сохранность значений.
- Ведомости проверяй на контрольных экземплярах с разными типами и значениями: количества, марки, материал, единицы, группировка, пустые поля. После перезагрузки сравни до/после, включая значения проекта.
- Перед массовой миграцией установи перечень проектов-потребителей и различающиеся шаблоны/привязки. Тест одной копии не подтверждает совместимость всех вариантов; проверяй каждый отличающийся вариант и сохраняй путь отката.

Поведение параметров подтверждай для целевой версии программы на копии семейства и проекта-потребителя.
